AUTOSAR BMS를 범용 RTOS로 재구현 — QEMU Cortex-M3 기반

AUTOSAR 기반 BMS 프로젝트의 태스크 로직(전압/전류/온도 측정 → 이상 진단 → 상태 관리 → 릴레이 제어)을 특정 프레임워크에 종속되지 않는 FreeRTOS 태스크 구조로 재구현했습니다. 실물 보드 없이 QEMU(MPS2-AN385, Cortex-M3) 환경에서 툴체인·링커 스크립트·startup 코드부터 직접 구성하고, 태스크 6개를 큐로 연결한 파이프라인을 설계·구현했습니다. 진행 중 CMSIS 표준 예외 핸들러 이름과 실제 FreeRTOS 포트 심볼이 불일치해 스케줄러가 무출력으로 멈추는 문제를 바이너리 심볼 분석으로 직접 진단·해결한 경험이 있습니다.

01

시스템 아키텍처

AUTOSAR RTE의 Sender-Receiver 패턴을 FreeRTOS 큐로 직접 옮겼습니다. 태스크 간 결합을 큐로만 허용하고, "데이터 성격에 따라 큐 depth와 대기 방식을 다르게" 설계한 것이 이 프로젝트의 핵심 판단 지점입니다 — 히스토리가 필요한 원시 측정값은 depth 5, 최신 상태만 의미 있는 값은 depth 1 + overwrite로 구분했습니다.

02

주요 기능 구현

FEAT · 01
FaultDiag
다수결 기반 노이즈 필터링

순간값 하나만으로 판정하면 센서 노이즈가 임계값 경계를 오갈 때마다 WARNING↔NORMAL 상태가 빠르게 반복되는 채터링이 발생합니다. 최근 5개 샘플을 링버퍼에 저장하고 3개 이상이 임계값을 넘어야 판정하는 다수결 방식으로 바꿔 순간 스파이크에 강인한 진단 로직을 구현했습니다.

fault_diag.c
/* 5샘플 중 3개 이상이 임계값 초과 시에만 fault 판정 */
for (int i = 0; i < bufferCount; i++) {
    if (data->cell_voltage_mv[cell] > CELL_VOLTAGE_FAULT_HIGH_MV)
        overVoltageFault++;
}
if (overVoltageFault >= FAULT_COUNT_THRESHOLD)
    xFaultState.fault_flags |= FAULT_OVER_VOLTAGE;
FEAT · 02
StateMachine
FAULT 래치(Latch) 상태 유지

한 번 심각한 이상이 감지되면, 그 원인이 일시적으로 사라졌다고 자동으로 정상 운전을 재개해서는 안 된다는 안전 설계 원칙을 반영했습니다. bFaultLatched 플래그로 FAULT 진입 이력을 태스크 내부에 유지하고, fault_flags가 다시 0이 되어도 명시적 리셋 전까지 FAULT 상태를 고수합니다.

state_machine.c
if (xFaultState.fault_flags != 0)
    bFaultLatched = true; // 한 번 래치되면 해제 안 됨

if (bFaultLatched)
    BMSState = BMS_STATE_FAULT;
else if (xFaultState.warn_flags != 0)
    BMSState = BMS_STATE_WARNING;
else
    BMSState = BMS_STATE_NORMAL;
FEAT · 03
RelayDecision
프리차지 3단계 내부 FSM

릴레이를 곧바로 닫으면 부하단 캐패시터로 인한 돌입전류가 접점을 손상시킬 수 있습니다. OPEN → PRECHARGE → CLOSED 3단계 상태 머신으로 릴레이 투입을 순차화했고, FAULT 발생 시에는 현재 어느 단계에 있든 즉시 OPEN으로 강제 전이하도록 설계했습니다.

relay_decision.c
if (xSystemState.state == BMS_STATE_FAULT) {
    eRelayState = RELAY_OPEN; // 무조건 강제 차단
} else if (eRelayState == RELAY_OPEN) {
    eRelayState = RELAY_PRECHARGE;
    xPrechargeStartTick = xTaskGetTickCount();
} else if (eRelayState == RELAY_PRECHARGE &&
    (xTaskGetTickCount() - xPrechargeStartTick)
        > pdMS_TO_TICKS(PRECHARGE_DURATION_MS)) {
    eRelayState = RELAY_CLOSED;
}
03

설계 의사결정

Queue Depth
by Semantics

데이터 성격에 따른 큐 깊이 차등 설계

히스토리가 필요한 원시 측정값(BatteryData)은 depth 5로 유지해 다수결 판단의 근거로 삼고, "현재 상태"만 의미 있는 값(SystemState, RelayCommand)은 depth 1 + xQueueOverwrite로 항상 최신값만 유지하도록 구분했습니다.

Fail-Safe
Latch

FAULT 자동 복귀 금지

일시적으로 이상 원인이 사라졌다고 자동으로 정상 상태를 재개하지 않도록 StateMachine에 래치 로직을 넣었습니다. 다만 현재 리셋 트리거 입력 경로가 없다는 한계는 README에 명시하고 후속 과제로 남겼습니다.

Deliberate
Simplification

프리차지 완료 판단의 고정시간 단순화

정석은 버스 전압이 팩 전압의 90% 이상 도달했는지로 판단하지만, 현재 데이터 구조에 버스 전압 측정값이 없어 고정 500ms 타이머로 단순화했습니다. 왜 단순화했는지와 원래 방식이 무엇인지를 코드 주석과 문서에 함께 남겼습니다.

Scope
Separation

SocketCAN 연동을 별도 프로젝트로 분리

bare-metal QEMU 펌웨어와 리눅스 커널 API인 SocketCAN은 실행 환경이 근본적으로 달라 같은 프로세스에서 연결될 수 없습니다. CANTx는 CAN 프레임 구성과 로깅까지만 담당하고, 실제 vcan0 브릿지는 리눅스 유저스페이스 기반 별도 프로젝트로 분리했습니다.

순간값이 아닌 추세 기반 판단
노이즈에 취약한 순간값 비교 대신, 히스토리를 유지하고 다수결로 판정하는 방식으로 바꾸며 실시간 시스템에서 필터링 설계가 왜 필요한지 이해했습니다.
🚧
스코프를 명확히 긋는 판단
SocketCAN 연동을 시도하다 bare-metal 펌웨어와 리눅스 커널 API가 애초에 만날 수 없는 조합이라는 걸 깨닫고, 프로젝트 스코프를 다시 정의했습니다. 계획을 계속 밀어붙이기보다 실행 환경의 한계를 먼저 확인하는 게 우선이라는 걸 배웠습니다.
🏗️
프레임워크가 가려주던 결정들
AUTOSAR RTE가 자동으로 처리해주던 태스크 간 통신 방식(큐 depth, 블로킹 여부)을 FreeRTOS에서는 직접 설계해야 했습니다. 프레임워크 뒤에 숨어있던 설계 판단이 실제로는 무엇이었는지 이번에 처음 명시적으로 마주했습니다.
📈
실측 기반 리소스 관리
스택 크기를 감으로 잡지 않고 uxTaskGetStackHighWaterMark()로 실측한 뒤 조정하는 방식을 익혔습니다. 추측이 아니라 데이터로 리소스를 튜닝하는 태도를 실제 코드에 적용해봤습니다.
